# Sensor Panel — Design Spec

**Status:** draft for review · 2026-11-20

A lightweight replacement for the AIDA64 sensor panel: a borderless window pinned to a
dedicated small display (currently 800×480), showing live hardware sensors, plus a
browser-based editor to design the layout.

## Goals

- **Reliable:** always on the right display, survives sleep / driver updates / monitor
  reshuffles, starts at logon with no UAC prompt.
- **Cheap:** target < 50 MB RAM and < 1% CPU at 1 Hz updates.
- **Customizable:** layouts edited in a web editor with live preview — widgets, shapes,
  colors, fonts, thresholds, graphs.
- **Resolution-independent:** one layout works on other panel sizes.

## Non-goals (for now)

- FPS counter (phase 4, via PresentMon).
- Fan control — read-only monitoring.
- Running on anything but Windows.

## Architecture

```
┌──────────────────────── SensorPanel.exe (C#, .NET 10, runs elevated) ───────────────────────┐
│                                                                                             │
│  SensorHub ──1 Hz──► SensorSnapshot ──► Renderer (SkiaSharp) ──► PanelWindow (borderless)  │
│   ├ LibreHardwareMonitor (CPU, GPU, mobo, drives, RAM)       ▲          on target display  │
│   └ Built-ins (time, date, drive letters, network total)     │                             │
│                                                       Layout (JSON)                         │
│                                                              ▲                              │
│  EditorServer (HttpListener, 127.0.0.1 only) ────────────────┘                              │
│   ├ serves editor web app (embedded static files)                                           │
│   ├ GET/PUT layout, GET sensor catalog, GET rendered preview frame                          │
│   └ WebSocket/SSE: live sensor values                                                       │
│                                                                                             │
│  TrayIcon: Open editor · Reload · Choose display · Exit                                     │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### One renderer, two consumers

The panel and the editor preview use the **same** Skia renderer. The editor shows a frame
rendered by the app (PNG over HTTP), with selection handles and drag outlines drawn in the
browser on top. This guarantees what you see in the editor is exactly what the panel shows,
and avoids keeping two rendering implementations in sync.

### Static layer ("baked background")

Layout elements are split into two layers:

| Layer | Contents | Rendered |
|---|---|---|
| **Static** | shapes (rect, rounded rect, circle, arc, line, polygon), gradients, static text/labels, imported images | once → cached bitmap; re-baked only when the layout or display size changes |
| **Dynamic** | widgets bound to sensors | every tick, on top of the cached bitmap |

Static elements stay in the layout JSON (fully editable); the baked bitmap is a cache, not
the source of truth. A user-supplied PNG can also be used as a static element (e.g. a
background designed elsewhere). Optional "export background" writes the baked PNG out.

### Sensor catalog

- Every LHM sensor is exposed by its stable identifier (e.g. `/amdcpu/0/temperature/2`).
- **Aliases** give friendly IDs and names: `cpu.temp → /amdcpu/0/temperature/2`,
  `"Fan #6" → "AIO Pump"`. Widgets bind to aliases so swapping hardware only means
  re-pointing an alias.
- **Formula aliases** (`"expr": "(cpu.power + gpu.power + 50) / 0.88"`) compute a value from
  other keys: `+ - * /`, `( )`, `min/max/abs`, `[raw-or-dashed key]`, `a ?? b`. A missing
  input or ÷0 gives no value. `Formula.cs` and the editor's `formula.ts` are twins and must stay in sync.
- **Templates & detection:** twelve built-in layouts (`src/SensorPanel/templates/*.json`, embedded,
  generated by `scripts/gen_templates.py`) are written against a fixed key vocabulary
  (`cpu.temp`, `gpu.fan`, `fan.1`–`6`, `pump`, `disk.read`, `net.down`, `drive.$1`…). `SensorDetector`
  maps that vocabulary onto whatever LHM reports on this PC: CPU Tctl/Package/Core Max, the discrete
  GPU over the integrated one (even when asleep), Super I/O fans that spin (GPU fan even at 0 RPM),
  the system disk by size, the busiest network adapter. A user's same-type aliases win over
  detection. `TemplateFitter` fills `$cpu.name`/`$driveN` placeholders and stretches the 800×480
  design to the panel (rects/lines/text boxes by x/y, circles/rings uniformly). Missing sensors show `--`.
  The first run builds `default.json` from **Duo**; the editor has a gallery and **Re-detect**.
- **Built-in sources:** `time`, `date`, `drive.C.usedPct` / `freeGB` (by drive letter),
  `fps` / `fps.low1` / `fps.frametime` (foreground app via PresentMon, phase 4),
  `net.down` / `net.up` (summed over physical adapters only).
- Only sensors referenced by the layout are updated each tick (LHM hardware groups that
  aren't used aren't polled) to keep CPU cost down.
- A rolling history buffer is kept for sensors used by graphs (retention = longest graph
  duration + 10 s, recorded on the poll thread). *(Implemented — phase 3.)*

### Widgets (dynamic layer, v1)

| Widget | Purpose |
|---|---|
| **Text** | Template with values: `"{cpu.temp:0}°C"`, `"{gpu.clock:0} MHz"`, clock/date formats |
| **Bar** | Horizontal/vertical fill, min/max, track color |
| **Ring gauge** | Arc with start/end angle, thickness, cap style (like the current CPU/GPU temp rings) |
| **Graph** | Line/area sparkline from history, fixed or auto range |
| **Indicator** | Shape/icon whose color changes with thresholds |

Common properties: position, size, rotation, opacity, font family/size/weight, colors, and
**threshold rules** (`>= 85 → red`) that can override any color property.

### Layout file & resolution independence

```jsonc
{
  "version": 1,
  "canvas": { "width": 800, "height": 480, "background": "#000000" },
  "scale": "fit",                 // fit (letterbox) | fill (crop) | stretch
  "aliases": { "cpu.temp": "/amdcpu/0/temperature/2", ... },
  "sensorNames": { "/lpc/it8665e/0/fan/5": "AIO Pump" },
  "static":  [ { "type": "roundRect", "x": 10, "y": 95, "w": 380, "h": 230, "r": 0, "fill": "#1a1a1a" } ],
  "widgets": [ { "type": "ring", "x": 30, "y": 160, "w": 130, "h": 130,
                 "value": "cpu.temp", "min": 20, "max": 100,
                 "color": "#ffffff", "track": "#3a3a3a",
                 "thresholds": [ { "gte": 85, "color": "#ff4040" } ] } ]
}
```

- Coordinates are in **canvas units**; the renderer scales uniformly to the actual display.
- Different aspect ratios: `fit` letterboxes; for a truly different shape (e.g. 1920×480 bar
  display), create a second layout.
- **Pages** *(phase 3)*: `settings.json` holds `pages` (layout file names, in order) and
  `pageSeconds`; the panel cycles through them, skipping pages that fail to load. Every page's
  sensors are polled each tick (aliases merged, first page wins on a conflict) so graphs keep
  history while their page is hidden. Editing goes through `GET/PUT /api/layout?name=`,
  `GET/POST /api/layouts`, `POST /api/layouts/rename`, `DELETE /api/layouts`, `PUT /api/pages`,
  `POST /api/show`. Names are validated plain file names inside the layouts folder.
- Layouts live in `%AppData%\SensorPanel\layouts\`; edits are saved atomically
  (write temp → rename) with a few rolling backups.

### Display pinning

- The target display is stored by its **hardware device path** (from the DisplayConfig API,
  EDID-based), not by monitor index or coordinates.
- On `WM_DISPLAYCHANGE`, resume from sleep, and a slow fallback timer (every 10 s), the app
  re-locates the display and moves/resizes the window to cover it exactly.
- If the display is missing, the window hides and waits; it reappears when the display returns.
- Window: borderless, tool window (no taskbar button, no Alt-Tab), topmost on its display,
  not activatable (clicks don't steal focus).

### Startup

- Task Scheduler entry: **at logon, run with highest privileges** → no UAC prompt.
- Requires the **PawnIO** driver (installed 2026-11-20 via winget). The app checks for it on
  start and shows a clear message on the panel/tray if it's missing.
- AIDA64's sensor panel should be disabled once this runs — both reading the Super I/O chip
  at the same time can produce garbage values.

### Editor (web app)

Served by the panel app at `http://127.0.0.1:<port>/?t=<random>` (ports 8737–8756), started
lazily from the tray and opened un-elevated via `explorer.exe`. *(Implemented — phase 2.)*

- Canvas preview: real frames from the panel renderer (`POST /api/render`), refreshed every
  second; the response also carries element bounds used for hit-testing and selection boxes.
  Select / move / resize with snap-to-grid (Alt disables), Shift keeps corners square.
- Toolbox: background shapes (rect, ellipse, line, label) and live widgets (value, clock, bar, ring).
- Inspector: geometry, colors (picker keeps `#rrggbbaa` alpha), fonts (system list), sensor
  binding, thresholds, opacity, bake-into-background toggle; with nothing selected — canvas
  size/scaling, aliases (rename updates references), sensor display names.
- Sensor browser: full catalog with live values (`GET /api/sensors`); while the editor is in
  use (API call within the last 120 s) the poll thread opens all sensor groups, then shrinks
  back to only the groups the layout needs.
- Layer list (reorder, hide), undo/redo (200 steps), keyboard shortcuts, import/export JSON.
  Save → `PUT /api/layout` → backup + atomic write → panel reloads.
- React 19 + MUI 9 + TypeScript (strict), bundled by Vite (`src/editor-ui`). MSBuild runs the
  npm build incrementally and embeds `dist/` (~740 KB incl. Roboto Latin) as `wwwroot/*`.
  State is a small `useSyncExternalStore` store; every edit clones the layout and records an
  undo snapshot (same-field typing / one drag coalesce into one step). `SENSORPANEL_WWWROOT`
  serves `dist/` from disk for development.

**Security:** the app runs elevated, so the server binds to `127.0.0.1` only, checks the
`Host` header (DNS rebinding), requires the random per-session token in an `X-Panel-Token`
header on every API call (constant-time compare), rejects foreign `Origin` headers (CSRF),
and serves the page with a strict CSP: scripts only from `'self'`; MUI's runtime `<style>`
tags are allowed via a random per-response nonce the server writes into `index.html`. The API never reads
arbitrary paths from disk. Images enter only as uploads (`POST /api/images`, ≤ 20 MB): they are
decoded, shrunk to ≤ 4096 px and re-encoded (PNG, or JPEG for JPEG input) into
`%AppData%\SensorPanel\images\` under a sanitized unique name; elements reference them by that
name only. Thumbnails are returned inline as data URLs.

### Resource budget

| Item | Approach |
|---|---|
| CPU | 1 Hz tick; only poll needed sensors; static layer cached; redraw only if values changed |
| RAM | WinForms host + SkiaSharp, no WPF/Electron/browser on the panel; target < 50 MB |
| Editor | Browser only loaded while editing; server idle otherwise |

## Phases

1. **Core panel** — SensorHub, renderer (ring, bar, text, static shapes), display pinning,
   tray, logon task, a default layout recreating the current AIDA panel. *Replaces AIDA.*
2. **Editor** — server, live preview, select/move/resize, property inspector, sensor
   browser with aliases/renaming, save/reload.
3. **More visuals** — graphs with history, gradients, image import, export baked
   background, multiple layouts per display, pages that rotate. *(Done.)*
4. **FPS** — PresentMon-based frame rate for the foreground app. *(Done.)*
   `FpsMonitor` runs `presentmon --output_stdout --v1_metrics --no_track_display/input/gpu
   --exclude dwm.exe` as a hidden child process. It runs only while the merged poll layout has
   an `fps*` key, in its own ETW session (`SensorPanelFps`), and a kill-on-close job object
   cleans it up. Rows are grouped by (pid, swap chain), with 10 s of frame times kept.
   - Each poll takes the foreground window's pid and its busiest swap chain. Browsers and
     Electron apps present from a GPU child process, so when the window's own process has no
     frames, it falls back to chains from processes with the same exe name.
   - `fps` = 1000 / mean frame time over 1 s; `fps.low1` = 1000 / p99 frame time over 10 s;
     `fps.frametime` = the mean frame time in ms.
